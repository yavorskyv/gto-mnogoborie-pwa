# Платформа «Герой ГТО» — полный сценарный план (реверс-анализ)

Составлено по анализу нативного приложения `ru.herogto.dev.participant` (Flutter) и его API-эндпоинтов в `libapp.so`. Бэкенд: `api.herogto.com` (в сборке — `api.dev.herogto.com`).

> Легенда достоверности: **[K]** — подтверждено кодом/эндпоинтами APK; **[В]** — обоснованный вывод из ролевой модели и архитектуры (собственных экранов судьи/админа в этом APK нет).

---

## 1. Принцип платформы
**Это операционная система проведения соревнований, а не витрина контента.** Единый бэкенд + несколько ролевых клиентов, всё завязано на сущность **«Событие»**. Логика: `заявка → допуск → судейство → результат → награда`.

- Единый API с версионированием и ролевыми пространствами: `/api/v1/participant/…` **[K]**, и (по namespace-архитектуре) `/api/v1/judge/…`, `/api/v1/admin|organizer/…` **[В]**.
- Аккаунты с ролями (`role` встречается в коде) **[K]**: участник, судья, организатор/админ, модератор.
- Офлайн-устойчивость на клиенте (SQLite, кэш `QrBadgeCache`) **[K]**.

---

## 2. Роли
| Роль | Зачем | Клиент |
|---|---|---|
| **Участник (атлет)** | Заявиться на события, иметь QR-пропуск, вести детей, грузить видео, видеть результаты/дипломы/рейтинги | Приложение участника **[K]** |
| **Судья** | Идентифицировать атлета по QR, фиксировать попытки (зачёт/No-Rep), результат | Судейское приложение **[В]** |
| **Организатор / Администратор** | Создавать и вести события, обрабатывать заявки, назначать судей, сводить и публиковать результаты, выпускать дипломы | Админ-панель (веб) **[В]** |
| **Модератор** | Проверка контента/заявок, поддержка | Часть админки **[В]** |

---

## 3. Доменная модель (сущности)
Из API и структур данных:

- **User / Auth** — аккаунт, роль, телефон+e-mail с подтверждением **[K]**
- **Participant** — анкета атлета (возраст, пол, ступень, регион, клуб) **[K]**
- **Child** — профиль ребёнка внутри семейного аккаунта **[K]**
- **QrBadge** — QR-пропуск атлета, выдаётся сервером, кэшируется **[K]**
- **Event (Событие)** — соревнование: даты, место, дисциплины, возрастные группы, квоты, команды **[K]**
- **Application (Заявка)** — заявка участника на событие + статус допуска **[K]**
- **Catalog** — справочники: дисциплины, возрастные группы, регионы **[K]**
- **Attempt (Попытка)** — попытка на станции: повторения, вердикт **зачёт/No-Rep**, результат, видео **[K]**
- **Team (Команда)** — командный зачёт **[K]**
- **Ranking / Record / Medal** — рейтинги, рекорды, медали, «мои лучшие» **[K]**
- **Diploma** — электронный диплом/сертификат **[K]**
- **File** — загрузка фото/видео (в т.ч. multipart) **[K]**
- **Notification** — уведомления (read/unread/settings) **[K]**

---

## 4. Сценарии по ролям

### 4.1. Участник (атлет)
1. **Регистрация**: телефон + e-mail, подтверждение кодом (`/auth/register`, `/auth/phone/confirm`, `/auth/verify-email`) **[K]**.
2. **Профиль**: заполнить анкету (возраст, пол, ступень, регион, клуб); добавить **детей** (семейный аккаунт) `/participant/children` **[K]**.
3. **QR-пропуск**: получить `QrBadge` с сервера — личность на событии **[K]**.
4. **Выбор события**: каталог событий `/participant/events`, справочники дисциплин/групп/регионов **[K]**.
5. **Заявка**: подать `/participant/applications`, отслеживать статус (на проверке / допущен / отклонён) **[K]**.
6. **На событии**: пройти отметку/мандатную комиссию (показать QR судье), выступить на станциях **[K/В]**.
7. **Видеофиксация**: снять попытку и загрузить `/participant/files/multipart` **[K]**.
8. **Результаты**: рейтинги, рекорды, медали, «мои лучшие», командный зачёт `/participant/rankings/*`; засуженные попытки `/participant/judging/attempts` **[K]**.
9. **Дипломы**: получить/скачать `/participant/diplomas` **[K]**.
10. **Уведомления**: статусы заявок, старт дисциплины, результаты `/participant/notifications` **[K]**.

### 4.2. Судья
1. **Логин** под ролью «судья» **[K роль / В клиент]**.
2. **Выбор события и станции/дисциплины**, к которым назначен **[В]**.
3. **Сканирование QR атлета** → подгружается участник и его заявка на дисциплину (однозначная идентификация) **[В, на базе QrBadge+сканера [K]]**.
4. **Фиксация попытки**: счётчик повторений, кнопки **зачёт / No-Rep**, финальный результат/время; при необходимости — видеофиксация как доказательство **[K сущности]**.
5. **Отправка вердикта** → привязка к атлету (`judging/attempts`) → в протокол **[K]**.
6. **Апелляция/пересмотр** — по регламенту (главная судейская коллегия) **[В]**.

### 4.3. Организатор / Администратор (админ-панель)
1. **Создание события**: даты, место, **дисциплины, возрастные группы, квоты, команды, станции**, регламент **[K сущности]**.
2. **Справочники**: ведение дисциплин / возрастных групп / регионов **[K]**.
3. **Обработка заявок**: допуск/отклонение, **мандатная комиссия** (медсправка, страховка, согласия) → смена статуса заявки **[K статусы]**.
4. **Назначение судей** на станции/дисциплины, координация коллегии **[В]**.
5. **Мониторинг хода** соревнования в реальном времени **[В]**.
6. **Сведение результатов**: агрегация попыток → **протоколы, рейтинги, рекорды, медали, командный зачёт** **[K]**.
7. **Публикация и дипломы**: выпуск дипломов/сертификатов, публикация итогов **[K]**.
8. **Уведомления**: рассылка участникам (допуск, расписание, результаты) **[K]**.

**Зачем нужна админка:** без неё некому создать событие, допустить участников, назначить судей и заверить результаты — приложения участника и судьи работали бы «в пустоту». Админка превращает регистрации и оценки в официальный ход соревнования и его итоги.

---

## 5. Сквозной сценарий соревнования (end-to-end)
```
ОРГАНИЗАТОР (админка): создаёт событие + дисциплины/группы/квоты, открывает заявки
        ↓
УЧАСТНИК: регистрируется → заполняет профиль/детей → подаёт заявку
        ↓
ОРГАНИЗАТОР: мандатная комиссия → допуск заявки (статус) → назначает судей
        ↓
СОБЫТИЕ: участник показывает QR-пропуск  →  СУДЬЯ сканирует → видит участника
        ↓
СУДЬЯ: фиксирует попытку (reps, зачёт/No-Rep, результат, видео) → вердикт
        ↓
БЭКЕНД: агрегирует → протоколы, рейтинги, рекорды, медали, командный зачёт
        ↓
ОРГАНИЗАТОР: публикует итоги, выпускает дипломы
        ↓
УЧАСТНИК: видит результаты/рейтинг, получает диплом; уведомления по всему пути
```

## 6. QR-логика (кто кого сканирует)
- **Судья → сканирует QR-пропуск атлета** (основное): идентификация «кого сужу», вердикт ложится в правильную карточку **[В на базе K]**.
- **Атлет → может сканировать** QR станции/события (отметка/check-in) или QR для подтверждения результата **[В, сканер в приложении есть [K]]**.
- QR-бейдж выдаёт сервер и кодирует ID/УИН участника **[K]**.

---

## 7. Карта API (v1)
**Auth [K]:** `register`, `login`, `logout`, `me`, `refresh`, `password`, `password-reset(/confirm)`, `phone(/confirm)`, `verify-email(/resend)`
**Participant [K]:** `applications(/)`, `children`, `diplomas`, `events(/)`, `files`, `files/multipart`, `judging/attempts/`, `notifications(/read, /unread, /settings)`, `rankings(/events/, /medals, /my-bests, /records, /teams)`, `catalog/(age-groups, disciplines, regions)`
**Judge / Admin [В]:** параллельные пространства `/api/v1/judge/…`, `/api/v1/admin|organizer/…` (создание событий, обработка заявок, назначение судей, ввод вердиктов, публикация итогов, выпуск дипломов).

## 8. Мэппинг на ваш проект (что есть / что достроить)
**Уже есть у вас:** генерация QR (карточка атлета), QR-сканер (jsQR), видеофиксация с записью, календарь 113 стартов, рекорды, регионы, калькулятор нормативов.

**Нужно достроить для полноценной платформы:**
- **Бэкенд + аккаунты/роли** (auth, участник/судья/админ) — сейчас у вас всё статично/локально.
- **Заявки на события** (подача, статусы, мандатная комиссия).
- **Экран судьи**: логин → выбор станции → скан QR атлета → ввод попытки (reps/No-Rep/результат) → отправка.
- **Админ-панель**: события, справочники, заявки, назначение судей, сведение результатов, дипломы, уведомления.
- **Протоколы/рейтинги/дипломы** на основе реальных попыток.

Порядок внедрения: (1) бэкенд+auth+роли → (2) события+заявки (админка) → (3) судейский экран → (4) протоколы/рейтинги/дипломы → (5) уведомления.

---

## 9. Оговорка
Роль «участник» и её эндпоинты **подтверждены кодом** APK. Судейский и админ-контуры **выведены** из ролевой модели и namespace-архитектуры API — их собственные клиенты в этот APK не входят. Это функциональная реконструкция логики, а не копия чужого кода/дизайна.
